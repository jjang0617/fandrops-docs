Not Scope / KPI·SLO

01 Not Scope — 의도적으로 안 한 것들
이 프로젝트는 "무엇을 만들었냐"만큼 "무엇을 하지 않았냐"가 중요합니다.
아래 항목들은 기술적 역량이 없어서가 아니라, 핵심 정합성 문제에 집중하기 위한 의도적 트레이드오프입니다. 7주라는 제한된 시간 안에 깊이 없이 여러 기능을 나열하는 대신, 동시성 제어·분산 트랜잭션·대용량 성능이라는 뼈대에 모든 리소스를 집중했습니다.
✕
실시간 채팅
WebSocket 인프라 복잡도가 높고, 핵심 도메인(주문·결제·예약)과 무관. 트래픽 정합성 증명에 집중.
✕
영상 업로드
스토리지·CDN·인코딩 파이프라인은 별도 도메인. 백엔드 트랜잭션 증명과 관련 없음.
✕
추천 시스템
ML 파이프라인·피처 엔지니어링은 별도 전문 영역. 팬덤 커머스의 핵심 기술 과제가 아님.
✕
완전한 MSA
초기부터 MSA는 운영 복잡도만 높임. 모듈러 모놀리스로 도메인 경계를 증명하고, 필요 시 점진 분리.
✕
모바일 앱
백엔드 포트폴리오 프로젝트. API 설계와 성능 증명이 목적이며, 클라이언트 구현은 범위 외.
✕
글로벌 다국어 / 다중 결제수단
MVP 범위 외. 단일 결제 API(토스페이먼츠) 연동으로 멱등성·Saga 패턴을 깊게 증명하는 데 집중.
우리의 입장
  • 위 항목들은 기술적 역량 부족이 아닌, 의도적 트레이드오프다.
  • 우리는 핵심 정합성 문제 — 동시성·분산 트랜잭션·대용량 성능에 집중했다.
  • 기능의 수가 아니라, 하나의 문제를 얼마나 깊이 파고들었는지로 평가받는다.
  • 추가 기능보다 장애 복구 가능성과 측정 가능한 수치를 우선했다.
02 KPI / SLO — 성공 기준

아래 5개 지표가 이 프로젝트의 합격 기준입니다. 기능 구현보다 이 수치 달성이 우선이며, 하나라도 미달이면 기능 추가 전에 원인 해결을 먼저 합니다.

구분 SLO (합격 기준) 측정 방법
정합성 오버셀·중복 예약·중복 결제 0건 부하 후 DB·이벤트 로그 검증
결제 복구 결제 실패 건 100%가 60초 내 보상(재고·상태) 완료 웹훅·Outbox·보상 이벤트 대조
Write 성능 주문/예약/결제 P95 < 300ms
(합의한 목표 TPS 기준)		 k6 + Grafana
안정성 5xx < 0.1%, 타임아웃 임계 이하 로그 / APM 집계
공정성·방어 Rate limit 위반 요청 429 처리
대기열 처리량 목표 달성		 차단 로그·대기열 depth
팀 규칙: 위 5개 중 하나라도 미달이면 기능 추가보다 원인 해결·튜닝을 우선한다. "동작한다"와 "수치를 증명한다"는 다르다. 모든 핵심 선택은 근거와 실험 결과를 남긴다.
03 팀 구성 — 도메인 오너십 (최종)

단순 역할 분배가 아닌 도메인 오너십 형태로 운영합니다. 각 오너는 코드 + 테스트 + 측정 지표 + STAR 트러블슈팅을 같은 도메인 산출물로 관리합니다. 도메인 경계는 "어떤 요청이 DB를 쓰는가"를 기준으로 나눴습니다. 읽기(GET)와 쓰기(POST·PATCH)가 다른 오너에게 분리된 경우, 경계를 명확히 문서화합니다.

왜 이렇게 나눴는가 기존 단순 "Auth / Product / Order / Payment" 4분할에서 실제 기능 규모에 맞게 재조정했습니다.

조회 도메인 경계 — 상품·피드가 핵심, 댓글은 정책 도메인 — 조회 트래픽이 집중되는 구간은 상품·피드·랭킹·배너·캘린더입니다. 정환철은 이 Read-Heavy 구간의 캐시·N+1·페이징 최적화에 집중합니다. 댓글·하트는 조회보다 금칙어·도배 방어·정책 처리가 핵심인 커뮤니티 정책 도메인으로, 쓰기와 조회를 모두 형성빈이 소유합니다. 조회를 굳이 분리하면 "댓글 GET은 누구 것인가"라는 경계 혼란이 생기고, 실익보다 관리 비용이 커집니다.

이벤트 계약을 단일 오너(장성재)로 집중 — Kafka 토픽·메시지 스키마·소비 파이프라인이 여러 도메인에 흩어지면 계약 변경 시 충돌이 잦습니다. 장성재는 주문·결제 흐름에서 발생하는 이벤트(결제완료·결제실패·재입고 알림 요청 등)의 계약과 버스·소비 파이프라인을 소유합니다. 단, 라이브 시작 등 이벤트 발생 주체가 Artist/System인 경우는 해당 도메인에서 트리거되며, 장성재는 그 이벤트가 버스를 타는 순간부터의 계약과 전달 파이프라인을 관리합니다.

표지민의 Communication 확장 — 인증·인가에 더해 OTP·SMS·알림 전송 실행까지 묶은 이유는, "누가 어떤 조건에서 메시지를 받는가"의 정책 판단이 Identity 도메인의 연장이기 때문입니다. 알림 발송 인프라 오너와 이벤트 계약 오너(장성재)가 분리되어 있음에 유의합니다.

05 아키텍처 원칙 (Engineering Principles)
  • 01 기능보다 정합성을 우선한다.
  • 02 기능 추가보다 장애 복구 가능성을 우선한다.
  • 03 추상화보다 측정 가능한 단순함을 우선한다. Premature optimization을 피한다.
  • 04 병목은 측정 후 해결한다. 추측으로 최적화하지 않는다.
  • 05 운영 가능하지 않으면 완성된 기능이 아니다.
  • 06 모든 핵심 선택은 근거와 실험 결과를 남긴다 (ADR).
  • 07 아키텍처는 모듈러 모놀리스로 시작해 성능 병목 도메인만 점진적으로 분리한다.
